## 1. 项目与请求链路

```text
微信小程序（体验版/正式版）
  └─ HTTPS https://wx.yzflab.top
       └─ 腾讯云服务器 111.231.58.244
            └─ Docker Nginx（life-nginx，host 网络，80/443）
                 └─ 127.0.0.1:8787
                      └─ Node 后端（systemd: life-sync）
                           └─ MySQL：life_workbench
```

- 小程序代码由微信开发者工具上传；Nginx 不负责托管小程序页面。
- 小程序登录页路由 `pages/login/login` 是前端页面路径；服务端登录 API 是 `POST /api/login`。两者不是同一个路径，也不要把 `/api/login` 填入微信“服务器域名”。
- 健康检查是 `GET /api/health`。它返回 200 只能证明该次健康检查链路可用，不等价于微信小程序的登录 POST 或数据同步已验收。
- 后端数据存储已配置为 MySQL。Redis 虽然安装运行，但当前后端 `package.json` 没有 Redis 客户端依赖，代码检索也未发现 Redis 调用；目前不能把 Redis 视为该项目的运行依赖。

### DNS/连通性注意事项

- 服务器公网 IP 是 `111.231.58.244`。此前不同机器/代理环境出现过 `198.18.*` 解析结果；不要把它作为 A 记录，也不要据此改服务器地址。应使用公网 DNS 核对：`dig wx.yzflab.top A @1.1.1.1` 或 `nslookup wx.yzflab.top 8.8.8.8`。

1. 在微信开发者工具确认当前体验版构建/上传时间和 `BUILD_VERSION`；重新编译上传后，手机删除旧体验版入口/重新进入最新体验版。确认实际环境为 `trial`，客户端请求必须是 `https://wx.yzflab.top/api/login`。

## 6. 部署时曾遇到的错误与避免重复踩坑

- **Node 路径错**：服务曾引用不存在的 `/opt/node-v24.2.0/bin/node`，所以 systemd 报 `status=203/EXEC`；后来确认的有效版本/路径为 `/opt/node-v24.21.0/bin/node`。服务器部署服务文件要用真实路径，而仓库模板的 `/usr/bin/node` 不一定适用于这台机器。
- **sudo 下 npm 找不到**：Node 是经用户 nvm 安装的，`sudo npm ...` 找不到 npm；普通用户执行 `npm ci --omit=dev` 曾成功安装 79 个包。服务运行所需 node_modules 必须实际位于 `/opt/life-sync-server/node_modules`，部署后以 `npm ls --omit=dev`/服务日志确认。
- **共享模块缺失**：`ai-insights.js` 引用 `../miniprogram/utils/` 下多个模块。后端归档本身不含 `miniprogram/`；曾出现 `Cannot find module '../miniprogram/utils/report-utils'`。确保共享工具打包完整并放在预期相对路径，不要只补文件直到下一个 require 再报错。
- **Nginx 容器端口显示空**：因其使用 host 网络，`docker ps` PORTS 为空是正常展示；检查 `docker inspect`、`ss -lntp` 和 HTTPS 请求，不要仅凭 PORTS 列判断 Nginx 未发布端口。
- **Caddy 不存在**：服务器曾返回 `Failed to disable unit: Unit file caddy.service does not exist`。当前实际前置代理是 Docker Nginx，不要再假设 Caddy 已安装，也不要让另一个服务抢占 80/443。
- **数据库账号/IP**：`ROOT_DB_OK` 曾成功；不要再新建数据库用户，不要猜 `DB_HOST` 或填 `178.18.0.1`。`DB_HOST` 当前值应由用户在服务器自行确认，回传时只需提供脱敏后的 host/port/name/user，不提供 password。
- **第一次创建 `.env` 与后续更新不同**：首次不存在时从样例复制一次是为了建立文件；现在 `.env` 已存在且已由用户填写。以后升级只部署程序文件，绝不要以 `cp` 样例覆盖它。

## 7. 数据安全、备份和待核实风险

- 曾贴出的 `docker ps` 显示 MySQL `0.0.0.0:3306->3306`、Redis `0.0.0.0:6379->6379`，也有 IPv6 映射。这表示容器端口绑定在所有宿主机接口；是否能从公网访问仍取决于云安全组/防火墙。应核对入站规则并将数据库/Redis限制在可信来源；若 Navicat 还要远程访问，先规划固定来源 IP 或 SSH 隧道，不能在未确认访问方式时直接断连。

**部署顺序强约束（本轮生效）**：v2.11 改了 settings 字段白名单（`theme:'auto'` + 3 个提醒字段），必须先部署 v2.11 server、再上传 v2.11 小程序；顺序颠倒会把主题保存打进「待同步-被拒」。

### v2.11 真机验收清单（写入交接，供逐项核对）

## 附注（2026-09-29 起）：新版打包与模块加载检查

本文前文描述的是历史部署过程。自本轮起，服务端部署物与共享工具的更新顺序固定为：

1. **现打新版包**：`RELEASE_VERSION=<版本> node server/scripts/pack-release.js`，产物在 `dist/`（含 `server/**`、共享的 `miniprogram/utils/**` 与 `manifest.json`）。仓库根目录的 `life-sync-*.tar.gz` 是历史归档，**不得充当新版包**。
2. **共享工具先就位**：解包新版包到服务器 → `npm ci --omit=dev`。
3. **模块加载检查**：`node server/scripts/check-runtime-modules.js <解包目录>/server` 必须全部 `CHECK_OK` —— `server/validation.js` 与 `server/ai-insights.js` 都跨目录 require `miniprogram/utils/`（含 `record-validation.js`），缺文件就是启动后 `Cannot find module` 事故的重演。
4. **再启动新版 server**，**最后**上传小程序版本（字段白名单变更版本先 server 后小程序的铁律见 RELEASE_CHECKLIST §2）。

## 头像和新功能的部署与隔离联调

- 先在独立测试目录安装新依赖并检查运行模块，再更新后端，最后上传使用新增字段和接口的小程序版本。头像处理依赖 sharp，部署需要 Node 20.9 或更高版本。
- 头像默认存于 `DATA_DIR/avatars`，可用 `AVATAR_DIR` 指向服务进程私有且可写的目录。账户只读取自己的头像，文件名由账号标识派生，版本由图片内容派生。反向代理沿用现有 API 路径和 128 KB 请求限制，小程序的同一 HTTPS 域名也需配置为下载文件合法域名。
- 每日备份单元同时归档 MySQL 和头像目录。恢复演练在隔离目录解包 `avatars_*.tar.gz`，将该目录设置为测试实例的 `AVATAR_DIR`，用同一测试账号核对头像读取。头像备份遵循数据库备份的默认 30 天留存设置。
- COS 就绪后保留头像接口和对象键，先复制并逐项校验私有对象，再切换头像存储实现。迁移前保留现有目录及备份。
- 隔离联调可使用 `DEV_MODE=1`、独立 `DATA_DIR`、回环地址与 SSH 隧道。`tests/new-workflows.test.js` 默认使用文件库。验证 MySQL 时设置 `LIFE_TEST_DRIVER=mysql` 并显式传入独立实例的 DB 配置。真实头像选择及微信订阅送达需用体验版真机验收。
